# Service foundation

Build owner boot JARs before the container images. Every application reads its owner database password from a protected mounted file, uses TLS verification, and listens for authenticated gRPC and management traffic only on the private network. Core HTTPS is published on loopback. PostgreSQL uses SCRAM and TLS; no database port is published.

Real owner migrations are supplied by their feature tasks. This foundation contains no production application-table migration. A missing packaged migration or incompatible/invalid history prevents readiness. Representative HTML and disposable SQL are integration-test resources and are excluded from boot JARs. Packaging the source SDL does not implement its business resolvers; domain gRPC handlers return the generated unimplemented status until their feature owners supply behavior.

Provision the CA, server/client certificate and key files plus distinct bootstrap, runtime, migrator, maintenance and backup password files outside the checkout. Secret files require owner read/write permissions. PostgreSQL copies required bootstrap files only into a protected tmpfs directory; its persistent database volume contains no working plaintext credential or TLS-key copies. Container UIDs must be able to read the mounted files; provision those ownerships before startup. Never use normal installation paths for tests.

Run `bash ops/bin/migrate.sh core`, then catalog and media, after privileged database preparation. The wrapper grants the selected migrator owner membership only for that operation and always revokes it. A per-installation file lock and an owner PostgreSQL advisory lock bound acquisition to 120 seconds; Flyway still manages its own history lock and validates checksums. Migration failure does not trigger repair. Inspect retained failure state and use an owner-reviewed forward migration or restore procedure.

These files establish the foundation only. Full lifecycle orchestration, seed/accounts, Media image processing, browser shell, business endpoints and release capacity evidence belong to later tasks.

## Shared admission agreement

Core account and browser delivery requires `spoolin.rate-limit.enabled=true`, a protected 32-byte `RATE_LIMIT_KEY_FILE`, and `spoolin.rate-limit.agreement-file` pointing to an operator-provisioned JSON file. Disabled or absent admission denies application requests; it never grants unlimited access. The agreement file must be a regular file with mode0600, at most4096bytes, containing exactly the string fields `profileRevision` and `keyCanary`. Neither the key, canary, file path nor user bucket digests belong in logs or public diagnostics.

Compute `profileRevision` as lowercase SHA-256 of UTF-8 lines `NAME=resolvedDecimalValue`, sorted by setting name, joined with one LF and no final LF. Include all ten `RATE_LIMIT_<PROFILE>_MAX_REQUESTS` / `_WINDOW_SECONDS` settings and `MCP_RATE_LIMIT_MAX_BINDINGS`, including defaults. Compute `keyCanary` as lowercase HMAC-SHA256 using the rate key over the ASCII bytes `spoolin-rate-agreement-v1`. Provision the same agreement and effective settings to every Core replica. Startup and each admission compare the resolved revision and locally computed canary with the protected mount. A missing, changed or mismatched agreement denies admission. No database connection is reserved for agreement.

Ordinary restart retains the same key, agreement and PostgreSQL counters. An operator transition explicitly replaces agreement and matching settings/key together; existing replicas reject the changed mount until restarted with matching configuration. A maximum change retains same-duration counters. A duration change creates new aligned buckets and does not promise a cumulative quota across revisions. A key replacement is an explicit operator transition that changes bucket identities. Never rotate it to clear exhaustion.

## Scoped actor trust

Enable `spoolin.actor.enabled=true` for the completed account/service boundary. Core alone receives `ACTOR_SIGNING_PRIVATE_KEY_FILE` (Ed25519 PKCS#8 DER, regular mode0600 file) and `ACTOR_SIGNING_KEY_ID`. Catalog and Media receive only `ACTOR_VERIFY_KEYS_FILE`: a regular bounded JSON map of one to four key IDs to standard-base64 Ed25519 X.509 SPKI DER public keys. Verifier files may be owner-only or publicly readable, but must not be group/world writable or symbolic links. The private signer is never mounted into Catalog or Media. Missing or invalid configured keys fail startup. An unconfigured receiver denies protected actor methods.

Distribute a new public verifier to all receivers and restart them before switching Core's signer. Retain the prior verifier for at least60seconds after the switch and until all old assertions expire; then remove it through an operator restart. Old assertions last at most30seconds with at most2seconds skew. Claims bind the exact receiver/method, account/session credential, current role/epoch, operation and correlation. Catalog performs the live Core check before protected dispatch; unavailable identity fails closed. Worker and probe SAN/method controls remain separate.

An operation query first meters a possible anonymous Core scope by source, then checks only its verified anonymous scope plus requested ID and permitted receipt kinds. Registration/sign-in receipts stay in that submitting scope after sign-in. Before attempting account-scoped or remote fallback, the query also meters the verified credential. Such fallback conservatively consumes both quotas; unknown and foreign IDs remain undisclosed. All selected query demands must admit before any result is dispatched. Original sign-out recovery additionally requires its original retained session and exact original intent; it does not grant live account authority.
