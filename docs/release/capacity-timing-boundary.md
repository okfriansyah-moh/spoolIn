# Core timing collection boundary

Capacity reader/writer installations enable the custom `spoolin.CoreRequestTiming` JFR event through the existing JVM options environment. Other installations leave recording disabled. The recording includes fixed operation names, fixed outcome/code values and the actual monotonic Core request-completion duration. Request documents, identifiers, variables, headers, URLs and stack traces are excluded. Client wall-clock measurements remain separate diagnostics.

Core writes `/var/spoolin/timing/core-timing.jfr` on graceful JVM exit, with a 128 MiB recording limit. The dedicated `core-timing` named volume preserves that file after the container stops; `/tmp` remains an ephemeral tmpfs and is unsuitable for this collection. The image initializes the timing directory with owner/group10001 and mode0700. The Core root filesystem remains read-only, capabilities remain dropped and the existing no-new-privileges policy remains enabled. The migrator does not inherit recording options or mount this volume.

The verifier must stop Core gracefully, copy the recording from the stopped owned container, parse the custom events and assert complete measurement accounting before reporting capacity results. A missing, truncated, unmatched or unparseable recording fails the timing proof. The diagnostic volume is outside the business backup manifest and contains no application state required for restore. Owned disposable CI teardown removes it with the other installation volumes. This source configuration supplies a collection path; it does not establish measured capacity or an accepted result.
