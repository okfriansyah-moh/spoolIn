# Catalog write receipt compatibility

The corrected Catalog writers use `catalog-write-v2` as an internal fingerprint marker. The existing owner HMAC key, actor scope, operation kind and policy revision remain part of receipt comparison. Operation IDs, persisted historical rows and retained key IDs are preserved.

The typed fingerprint covers movie values and date precision, optional-field presence, expected-version presence/value, person biography, role category/label, credit identities, ordered character arrays, ordered countries and update masks. Genre sets and masks use stable sorted set order. Repeated values have explicit counts and indexed entries, so delimiter characters cannot merge distinct arrays. Each string is represented by its exact UTF-16 code units encoded as Base64 before the existing length-delimited HMAC input. This preserves even rejected surrogate sequences until validation, avoiding replacement-character collisions. The encoded strings are temporary comparison inputs; they are never persisted as payloads or sent to logs.

Fresh writes compare the submitted policy revision and validate effective fields inside the owner receipt transaction. A matching completed version-2 receipt returns its original outcome without applying a later policy to the historical write. Current authorization and owner lookup rules continue to apply. Policy tightening does not rewrite unchanged stored text.

Earlier fingerprints omitted some request values. Their historical hashes cannot establish equality of those omitted values. The corrected write endpoint therefore fails closed with `IDEMPOTENCY_CONFLICT` for an old-format receipt, including a seemingly identical retry. It neither rewrites that hash from guessed audit data nor repeats the domain effect. Authorized `GetOperation` still returns the original retained outcome. After ordinary result expiry it returns the existing minimal terminal state with `resultExpired`; expiry never authorizes execution again. Clients must retain the original operation ID and resolve that outcome, without automatically allocating a replacement UUID.

The implementation also preserves the approved blank/absence rules: omitted patches retain values, explicitly null or trimmed blank optional text clears, and nonempty optional text uses effective limits. A release-date patch replaces and validates the whole partial date tuple. Existing-record writes require the wire's expected-version presence, including a present zero for an initial version.

Remote verification is pending. The added unit checks and real signed mTLS/PostgreSQL tests cover complete field comparison, changed-content conflicts, concurrent replay, lost-response recovery, policy changes and retained old-format receipt lookup. These tests do not replace application/browser or assisted-client acceptance.
