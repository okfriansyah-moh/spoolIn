# Remote capacity measurement

This source implements one selected phase per invocation of `python3 ops/ci/verify-capacity.py --phase PHASE --repetition N`. It does not establish execution or acceptance. T045 and ATDD-211 remain pending until their complete current evidence and the combined independent review support closure.

The coordinator runs `startup`, `reader` and `writer` for repetitions 1, 2, 3, then `plans` for repetition 1. Heavy execution is limited to verified GitHub-hosted Linux. Pause the source and restored installations first; the helper refuses concurrent installations belonging to this run. Each invocation provisions a new finite capacity namespace through the existing protected preparation script, with fresh accounts, keys and nonce ledgers. Cleanup removes only that exact namespace and its disposable volumes. Failed evidence stays under `artifacts/capacity/PHASE-N/`. Do not reuse a failed namespace or erase failed reports to repeat it; use a new actual workflow attempt.

Each installation starts with the actual `make start` command, followed by `make status`. All eight runtime images must exist before startup; before/after image IDs distinguish warm images from rebuilding changed inputs. Startup repetitions compare the complete command's monotonic elapsed time strictly against 120 seconds. The startup script's 300-second readiness limit remains a separate operational control. The capacity report retains readiness and the declared runner CPU, RAM, disk, OS, architecture, image, run identity and Git SHA.

Before workload admission, the helper verifies the selected READ and MUTATION profiles are 1000000 requests/60 seconds in the actual Compose configuration. It checks the protected Core configuration enables rate admission and retains the protected agreement's profile revision. Reader requests use normal READ/SOURCE admission. The prepared Maintainer signs in normally and writer requests use normal MUTATION/CREDENTIAL admission; CSRF and cookie material stay in memory. Durable admission counter observations supplement source/HTTP proof. No limiter is disabled or bypassed.

The initial database comparison imports the existing complete seed verifier's field, identity, relationship and provenance assertions. It requires exactly 100 movies and 100 series. This baseline comparison does not substitute for the separately owned rendered artwork, complete API seed and restart acceptance.

Reader repetitions run ten closed-loop readers without think time. Each reader cycles five fixed classes equally: unfiltered first 20, rare literal, common literal, type plus two genres and year/month, and title detail. Expected identities and ordering come independently from the approved frozen manifest. Before load, each actual HTTPS result is compared with that expected scope. Cold diagnostic requests are retained separately. Warmup lasts 60 seconds and drains completely before the measured 300-second offer window begins; measured in-flight requests then drain before evidence capture. The writer runs separately with concurrency 1, cycling movie synopsis, person biography and a role-compatible credit character update equally. It retains original intent identity on uncertainty, stops instead of retrying a possibly committed mutation under another UUID, and compares final versions/fields through a fresh database read.

Raw client samples retain sizes, HTTP status, typed safe error code, transport error/timeout, assertion result and client elapsed time. Client elapsed time is diagnostic and never becomes Core latency. The optional Core recording contains only the custom `spoolin.CoreRequestTiming` event; the Core boundary records monotonic duration and fixed operation/outcome/code fields. A successful capture must flush to the private `/var/spoolin/timing/core-timing.jfr` volume path before extracting the stopped Core container's recording. The helper extracts only safe fields with the pinned JDK tool, filters the independent measured window, rejects unknown event types/enums and requires complete sample accounting. Binary recordings and intermediate JFR JSON stay in protected runner temporary storage and are excluded from uploaded evidence.

For each repetition independently, sort all selected Core durations and take sample `ceil(0.95*n)`, one-based. Retain typed domain outcomes in this population and report successful-request p95 separately. There is no pooling across runs. Empty selection, incomplete samples, throttling, errors, scope failure, class imbalance, an aborted writer or equality with the 300 ms/500 ms threshold prevents a passing workload result. Counts identify offered requests, completed HTTP requests, admitted HTTP200 completions, throttled requests and each error category. Transport failures retain their elapsed/censoring observation separately.

The plans phase uses a different installation. It captures actual `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on the 200-title baseline and a controlled 100000-title stress fixture. The fixture is explicitly database setup for the assigned capacity case; it is never UI or seed-provenance proof. Source-derived title projections and parameterized rare/common/no-filter/two-genre predicates, unknown dates, private-credit visibility, due/exhausted worker, resolved purge, nonce reservation and rate admission/expiry shapes retain their SQL, parameters, source hash and actual plan. The 100k fixture also receives the same five real application request classes, compared with independent database scopes, without inventing a stress latency budget. Plan queries run within rolled-back transactions. A 200-row sequential scan is not automatically a defect, and this support introduces no index-use threshold or deployment service-level objective.

Remaining obligations retain explicit pending status: accepted JPEG/PNG/WebP processing below 10 seconds near resource boundaries; overload and unrelated metadata behavior during Media faults; graceful/forced restart, disk pressure and measured persisted recovery; protected restore RPO/RTO and selected external provider evidence; both arm64 and amd64 resource observations; SQL families outside this selected TD 7.4/7.5 inventory and required architecture coverage. Existing owner evidence may satisfy an obligation only when its actual source, configuration, tools and artifacts match the final selection. Each selected-phase success is narrower than ATDD-211 or formal selection acceptance.

The remote rule-regression command is `python3 ops/ci/verify-capacity-test.py`. It checks measurement selection, nearest-rank/equality/error accounting, privacy and refusal rules. It does not run the workload or replace any runtime proof.

The plans phase now selects its result from actual completed checks rather than returning a fixed pending result. Its checked inventory names all fifteen plan families from TD 7.4/7.5, retains each owning production source path/hash and requires every family on both the 200-title and 100k-title fixtures. It adds people lookup, protected account lookup and draft expiry to the earlier plans, uses the actual title/person/credit search expression and preserves the resolved-work retention predicate. Lookup parameter values and quoted plan literals are withheld; executed timing, row counts and plan structure remain available. Plans use paused writers and bounded rolled-back transactions. Named synthetic work fixtures are removed only when they have no actual attempt history, before application writers resume. Unknown-date and archived-parent states are explicit plan fixture changes after the complete initial seed comparison; they do not establish seed acceptance.

The same owned PostgreSQL process loads its available `pg_stat_statements` extension after stopping application writers and restarts through Compose. Existing preload entries are preserved. Missing extension support, failed restart, missing statements or counter reset fails the phase. The helper resumes the real `make start` application and measures actual Catalog runtime-role completed top-level SQL around serialized HTTPS list requests returning 1, 20, 1 and 20 titles. It retains normalized emitted SQL, call/row/execution-time deltas and response sizes/statuses. Metadata SELECTs are counted separately from observed work/health activity; all deltas remain in the report. No other metadata client runs against this owned fixture. A growing or unstable metadata query count fails; observing source code alone cannot pass this check. This is a real emitted-SQL boundary observation, distinct from the source-bound parameterized plan artifacts.

Run `python3 ops/ci/verify-capacity.py --phase plans --repetition 1` after stopping other installations from the same workflow attempt and building the actual pinned images. No workflow preload flag is required: the helper configures only its fresh owned PostgreSQL instance. The normal READ limiter remains enabled at the already validated positive benchmark quota. The source regression command remains `python3 ops/ci/verify-capacity-test.py`. Neither command has been run during authoring. Reader oracle matching now includes active credited CAST/CREATOR people and excludes archived titles/people, matching the production literal-search scope.

SQL counting retains two independent selections at each dataset size: the root title list with genres/provenance/artwork, and the original full benchmark selection including `Title.credits`. Both must keep stable call counts for a selected-phase pass. The production nested field currently invokes one TitleCredits RPC per returned title; the approved existing RPC carries one title identity. The evidence helper preserves this nested selection and will report measured growth as a failure, while still executing the independent plan families. Root-list batching alone cannot satisfy the full nested-field obligation. Resolving that production path requires its owning implementation and approved contract handling; this helper does not add a batch RPC, alter DTOs or infer closure from the inventory.
