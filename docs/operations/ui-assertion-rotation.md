# Private UI assertion keys and validation

This implementation covers private MCP-to-Core assertion primitives. It does not establish either assisted client's host isolation, deliver protected review-frame credentials, or enable publication. Keep `MCP_PUBLICATION_ENABLED=false` until the required client-specific host enforcement has actual evidence.

The existing active selectors remain `MCP_UI_ASSERTION_KEY_ID` and `MCP_UI_ASSERTION_KEY_FILE`. Core and MCP share this separate32-byte MAC key; they do not reuse connector, actor-signing, CSRF, rate, cursor or operation-comparison material. A key ID uses1–64 ASCII letters, digits, underscore or hyphen. Key files must be absolute regular files, exactly32 bytes, mode0600, with no final symlink. Mount only into the two authorized services. Never print or place keys, assertions, challenges or connector bearer credentials in model-visible content, URLs, screenshots or logs.

Core accepts an optional complete previous-key triple:

| Setting | Meaning |
| --- | --- |
| `MCP_UI_ASSERTION_PREVIOUS_KEY_ID` | Previous distinct key ID |
| `MCP_UI_ASSERTION_PREVIOUS_KEY_FILE` | Protected previous32-byte file, distinct material |
| `MCP_UI_ASSERTION_ROTATED_AT` | Absolute Unix-second activation time of the new write key |

The previous key is eligible only while `ROTATED_AT <= now < ROTATED_AT + 60`. Equality at the deadline rejects it. The timestamp must not be future-dated and is retained unchanged across restarts. Restarting with the same descriptor cannot extend the read window. The active key remains available after that window; expired previous-key material is cleared from the verifier's in-memory ring when selected again. Remove the complete previous-key triple after the window, then retire its mounted read file under the operator's custody policy. Do not change the recorded timestamp to prolong an existing read window.

For a coordinated rotation, pause new approval/rejection issuance, generate a fresh separate key and ID in protected operator/CI storage, install the new active selectors in both services, and record one absolute activation timestamp for Core's old-read descriptor. Use `UiAssertionSigner.rotate(newId,newFile)` for an already-held signer or recreate it from the new active configuration while issuance is paused. Rotation installs only the new write key and zeroes the retired in-memory signer buffer. Resume only after both components use the intended new active key; allow old reads for at most the fixed60-second window. Rolling deployments must finish inside this budget or remain paused. Configuring key material does not authenticate a supported host channel.

The signer validates exact runtime fields rather than trusting TypeScript types. Connector, transport session, proposal and invocation identifiers are full lowercase UUID strings. Revision is an integer in1..2147483647; client is `CLAUDE` or `CHATGPT`; the only methods are `/spoolin.v1.McpGatewayService/ApproveMovie` and `/spoolin.v1.McpGatewayService/RejectMovie`. The private RPC hash uses the existing protobuf/Catalog32-byte digest encoded as strict padded Base64. Core matches it exactly to the request. Public MCP schemas separately require lowercase hexadecimal; the public projection and approval conversion still require their actual boundary correction and evidence. This private primitive does not silently change those public contracts.

The payload is deterministic UTF-8 JSON with sorted keys and exactly audience, client, connector, expiry, hash, invocation, method, proposal, revision and session. Audience is `core`; expiry is an integer strictly after the verifier's time and no more than30 seconds ahead. The token uses unpadded base64url payload/MAC and remains at most4KiB of private RPC metadata. Core verifies the exact key ID and HMAC-SHA256 before parsing. It rejects duplicate JSON fields, trailing content, unknown fields, type coercion, alternate JSON/wire encodings, wrong actor/client/method/proposal/revision/hash, invalid UUIDs, revoked/expired connector records and expired assertions. Invocation replay admission is synchronized and bounded to10,000 live entries.

The in-process replay cache is not durable across Core restarts. The owner still enforces the persistent proposal challenge, exact immutable revision and durable operation receipt; those actual restart/replay boundaries must be exercised separately. A consumed assertion whose downstream request fails is replaced with a fresh invocation when the authenticated host retries the same exact intent; the durable owner result governs duplicate effects.

Session authority follows the approved adapter delegation: the signer may be called only after an installed supported host authenticates its private app channel, resolves its live connector-bound session and binds that session UUID to the exact invocation. Core authenticates the adapter at the existing mTLS gateway and verifies its signed session claim. The current repository has no authoritative second Core-side copy of the adapter's HTTP session and specifies no additional host attestation/header protocol. No untrusted header or test-only resolver is introduced. The production MCP session handler currently does not call this signer from a verified host UI channel; host/session provenance and protected challenge/bearer delivery remain explicit implementation and actual-client obligations. Syntactic session validation alone is not claimed as host compatibility or full session-flow acceptance.

`UiAssertionVerifierTest`, `UiAssertionKeysTest` and `mcp/test/identity/ui-assertion.test.ts` contain remote-executable tests for exact bindings, malformed signed input, replay concurrency, protected files, lifecycle closure and absolute key overlap. They must run on the intended remote revision. Source presence or these authored tests do not establish execution. Actual gateway mTLS, live host approval/rejection, durable owner challenge/replay and client isolation require their own real boundary evidence.
